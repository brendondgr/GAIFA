# GAIFA

**GAIFA** stands for *Great, Another Interface For Agents*, said "guy-fuh". It was called AIHub until 2026-10-25 (plan Phase 50); old commits keep that name.

One local app (FastAPI hub on `127.0.0.1:7000`) that controls every AI service on this machine. Each service is a **mod**: a folder in `services/<id>/`, run as its own process. Plans: one file per plan in [docs/plans/](docs/plans/README.md); the original build plan [docs/backend-plan.md](docs/backend-plan.md) (Phases 0–51) is closed. UI brief: [docs/design-brief-ui.md](docs/design-brief-ui.md).

## Layout
- `utils/`: hub code (Python package) · `services/`: mods · `web/`: the UI (Claude Design `.dc.html` format; revision 2 built here, see `web/PATCHES.md`)
- `data/models/` (nothing in it is tracked: the registry is each machine's own) · `data/databases/` · `outputs/<mod>/<date>/`
- `config.toml` is this machine's (gitignored), made from the tracked `config.example.toml` on first run: change defaults for everyone in the example, your own settings in `config.toml`. The same for `services/lcpp/data/models.json` (plan 23.11).
- `docs/`: architecture, plan, UI brief, `reference/` UI exports

## Commands
- `uv sync`: install hub dependencies into `.venv/`
- `uv run pytest`: the test suite (`utils/tests/`)
- `uv run python app.py`: run the hub in the foreground on 127.0.0.1:7000 (`/api/docs` for the API)
- `gaifa setup [<mod>…] [--plan] [--json]`: install GAIFA or some mods (the hub, host checks, mods, models, checks); one process for a person and an agent (`--help` for answers and exit codes; skill `gaifa-setup`). `gaifa docs [--check]`: the setup docs index.
- `gaifa new <id>`: a new mod from `services/_template/`, installed and loaded; `gaifa rescan` after adding or removing mod folders by hand.
- `gaifa models list | show <id> | scan [--add] | verify <id>… | --all`: the models registry.
- `gaifa status | start | stop | restart | logs [id] [-f] | doctor [--inventory] | open`: the hub as a systemd user service (logs read `data/logs/<id>.log`) (`gaifa install` writes `~/.config/systemd/user/gaifa.service` and links `~/.local/bin/gaifa`). After changing hub code, `gaifa restart`. `gaifa doctor` checks the whole install (also Settings → About).
- `gaifa backup <folder>`: databases, registry, `config.toml`, the mods' `.env` files and their small settings files (`data/state/<id>/*.json`, such as the workspace folders) in a dated archive.
- `gaifa repos [status | fetch | update <id> [--commit] | pin <id> | sync]`: `relay`, `lcpp`, `tts` and `gen3d` are submodules of their own repositories (plan mod-repos): what each is pinned at, what's new on GitHub, problems with their fix; `update` installs, restarts, checks and rolls back on failure.

## Mod contract
Full how-to: [docs/mods.md](docs/mods.md). A mod is done when `gaifa check <id>` passes.
1. `services/<id>/service.toml`, with `id` matching `[a-z][a-z0-9-]{1,31}` and the folder name.
2. An HTTP server on `127.0.0.1:<port>`, in any language.
3. A health route that returns 2xx when ready.
4. Optional extras (memory, status, outputs, UI, widgets) are listed in architecture §4.2.
5. Deleting `services/<id>/` removes the mod completely.

## Setting up a new machine
Run `bin/gaifa setup`, or follow the `gaifa-setup` skill to do it for someone: ask which mods and models they want, show `gaifa setup --plan`, run it with their answers, hand them any `sudo` command or prompting step, and confirm every check. Guide: [docs/setup/README.md](docs/setup/README.md); each mod's setup is in `services/<id>/setup/*.md`.

## Testing on another machine
To find what breaks on a new kind of machine (another GPU, WSL2, macOS), follow the `gaifa-field-test` skill: record the machine (`bin/gaifa hardware`), ask which mods to try (by default all that are available), show `bin/gaifa setup --plan --smoke`, run it with `--smoke`, try each failure's documented fixes for a short while and record every attempt with `bin/gaifa report note "…" --setup <id> --cmd … --output <file> --tried …`, run `bin/gaifa doctor`, then `bin/gaifa report` and give the person its path. Change no tracked file unless asked; a local workaround is kept in the report's `git diff`. The report (`data/state/reports/<date>-<host>.md`) is written for whoever fixes GAIFA: each issue names the setup doc line, the command, its log and a likely cause.

## Rules
- **No GitHub Actions.** The user turned CI off on 2026-10-22 (the `tests` workflow is disabled on GitHub and `.github/workflows/` is gitignored): never add or commit a workflow. Tests run here, before every commit.
- **The Auto judge is only ever a decision model** with a structured answer: the `decide` mod's d3-lite (`[agent.judge]`, `utils/tools/judge.py`). Never a chat model through the relay, and never Gemma 4 26B: a chat model takes seconds per link and isn't built for this (the user's rule, 2026-11-08; plan web-approvals).
- **Never run `git clean -x` or `git clean -X`.** They delete ignored files, which here means ~190 GB of model weights.
- **Four mods are their own repositories** (git submodules, plan mod-repos): `relay` (brendondgr/Relay), `lcpp` (LLMs), `tts` (LocalTTS), `gen3d` (3DGenerate). A change to one is two commits: first in the mod (`git -C services/<id> …`, its own tests, push), then GAIFA's pin (`gaifa repos pin <id>`, `uv run pytest`, commit). Check `gaifa repos status` before committing GAIFA; never commit an unpushed pin, force-push a mod, or `git submodule update` over a mod's changes. A clone needs `--recurse-submodules` (or `gaifa setup`/`gaifa repos sync`); a GAIFA worktree has empty mod folders, so work on a mod in a worktree of its own repository. Workflow: docs/mods.md §10.
- Nothing is written outside the project root, except the allowlist in plan Phase 12.4 and folders the user set to Edit or above in the workspace mod (plan Phase 27). The allowlist includes SearXNG's `settings.yml`, its `settings.yml.gaifa-<date>` backups (the newest 10) and the temporary `.settings.yml.gaifa-new`, written by the `searxng` mod (plan 26.3). The GAIFA folder and `data/models/` never go above Read.
- Mods talk to the hub only over HTTP.
- No import-time side effects.
- Tests pass before every commit. Commit message style: `GAIFA (<plan-slug> 2.3): Service state machine with health checks` (the plan's file name in `docs/plans/`; older commits are `GAIFA (2.3): …` for backend-plan steps).
- **Plans:** every new plan is its own file, `docs/plans/<slug>.md`, listed in `docs/plans/README.md` (skill `plan`). Never add phases or steps to `docs/backend-plan.md`.
- Keep `docs/` in sync with behavior, in the same commit. That includes `docs/structure.md` when files are added, moved or removed.
- Files under ~500 lines; split any that pass 800.
- A new mod ships a setup doc, `services/<id>/setup/<env>.md` with a `gaifa-setup` block (summary, steps, check, optional model suggestions; docs/mods.md §9), and `gaifa docs --check --strict` passes. Setup docs describe the mod, never one machine's models.
