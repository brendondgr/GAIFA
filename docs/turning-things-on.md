# Turning things on

One page for a person or an agent: what each part of GAIFA gives, how to turn it on, and what its state means. Plan [capability-enablement](plans/capability-enablement.md). The whole setup process, host first, is [setup/README.md](setup/README.md).

**The quickest way.** Paste the text this prints into your coding agent (Claude Code, Codex):

```bash
gaifa setup --prompt web searxng workspace decide embed
```

It tells the agent where GAIFA is, which docs to read, which commands to run and how to check each mod; your agent asks you the same questions `gaifa setup` would. Name the mods you want; `gaifa setup --recommended` sets up the set recommended for chat (below) without a list.

## Three ways to turn one on

1. **Your coding agent** (the one you already use). `gaifa setup --prompt <mod>…` prints the text to paste: it reads the mod's setup doc (`services/<mod>/setup/`), runs `gaifa setup <mod>` with your answers, runs the doc's **Check**, and uses its **When it fails** table when something breaks. The Set up dialog's *Have your coding agent do it* gives the same text with a Copy button.
2. **The app.** A mod that isn't on shows why on its page, with the button that fixes it: *Set up*, *Turn on* or *Start*. Settings → Services lists every mod with its state, **Set up**, **Test** and its switch; the Overview's *Needs you* tile lists what a chat is missing. *Set up* opens the Set up dialog: what it installs and where, the downloads with their sizes and licences, the questions, then *Set it up here* (it runs `gaifa setup` for you and shows each step).
3. **GAIFA's agent.** Ask in a chat ("set up web search", "turn on the calendar"). It reads the plan (`hub_setup_plan`) and proposes the setup (`hub_setup`), which waits for your yes on a card; a mod that is set up but turned off it turns on by itself (`hub_enable_service`) when a chat needs it, and a stopped mod starts on its first call.

## What a mod's state means

| State | Means | What turns it on |
|---|---|---|
| **on** | running (or starting) | — |
| **starts on use** (*stopped*) | set up and turned on, not running: the first call to its tools starts it | nothing; or `gaifa start <mod>` |
| **off** | turned off (`[services.<mod>] enabled = false`): kept installed, not started | its switch in Settings → Services, or the agent |
| **not set up** | its environment isn't there: `gaifa setup <mod>` never ran on this machine | one of the three ways above |
| **can't run** | its recorded variant needs hardware this machine doesn't have (a CUDA build without an NVIDIA GPU) | `gaifa setup <mod> --accel <mod>=<accel>` with one this machine has (`gaifa hardware`) |
| **failed** | its process failed, or its last start did | its log (`gaifa logs <mod>`, *View logs*), then *Start*; the setup doc's **When it fails** |
| **broken** | its `service.toml` has errors | the errors on its page; `gaifa check <mod>` |

A chat knows all of this: a tool of a mod that isn't on is still listed for the agent, and its call answers at once with the state and the fix (`capability_unavailable`) instead of failing slowly. `gaifa doctor`'s **What works** says it per mod.

**Turning one off.** Its switch in Settings → Services. Because the agent turns a set-up mod back on when a chat needs it, keep one off for the agent by putting `hub_enable_service` under Settings → Permissions → Never run. **Removing one:** delete `services/<mod>/` (the mod contract: that removes it completely).

## Search: your SearXNG or GAIFA's own

Web search (the `web` mod's `web_search`) asks a SearXNG; reading pages (`web_fetch`) needs none. `gaifa setup searxng` asks which:

- **Yours**, if one already answers (found on port 8080, or the port you give it), with JSON results turned on. GAIFA watches it and can change its engines and settings, with a backup each time.
- **GAIFA's own**: a container `gaifa-searxng` from SearXNG's image pinned by digest, on `127.0.0.1:5200` (the next free port up to 5209), with podman (or Docker), started and stopped with the mod.

The SearXNG page's first card says which one search uses and whether it answers, with *Start GAIFA's own*, *Use mine on port …* and *Remove GAIFA's SearXNG*. The Web page says *Search isn't connected* with *Connect search* when none answers.

## Chat's model: the relay or your own server

`gaifa setup agent` asks first how Chat reaches a model:

- **GAIFA's relay** (the default): it runs local engines (llama.cpp, vLLM), holds your provider keys (Claude, OpenAI, Gemini) and draws usage charts; Settings → LLMs holds its servers, keys and engines.
- **A server you already run**: any OpenAI-compatible `/v1` URL, a key if it needs one, and one of its models. No relay is set up; Settings → LLMs' servers and keys, the usage charts, GAIFA's GPU slot per request and cloud models aren't there, and a model whose facts the server doesn't give is assumed to have an 8,192-token window, tools on and pictures off.

Settings → LLMs → *Chat's server* shows which one, whether it answers, **Test** and *Switch to the relay*. When nothing answers, the Chat page says so in a banner with the one fix that applies.

## The decision model and embeddings

`decide` (the Auto judge's decision model) and `embed` (search by meaning, chat search, the agent's memory) are tested on your machine when they are set up: one sentence each ("d3-lite on your GPU: 0.04 s per answer, 7.7 GB"), with advice when a test fails or runs on the CPU though a GPU was expected. Both offer smaller models: [embed-models.md](embed-models.md) compares embedding models measured here, and any decision model can be the judge (`services/decide/README.md`, *Adding a decision model*). Change the embedding model in Settings → Agent → Memory (**Change…**); its new index is built in the background while search keeps working.
